# Порядок разработки

## Источники истины

Приоритет: последние решения пользователя → `AGENTS.md` → текущие ТЗ/operating-rules и принятые `DECISIONS.md` → задача в `TASKS.md`. Исходник 1.0 и старый proposal не возвращают отменённые требования.

`STATUS.md` — короткая точка входа. `TASKS.md` — единый список объёма и статусов. `WORKLOG.md` — доказательства выполненных действий; старые записи не переписываются как будто поздний результат был известен раньше. Ошибки исправляются отдельной записью.

## Статусы задач

| Статус | Значение |
|---|---|
| BACKLOG | Задача определена, зависимости или уточнения ещё не закрыты |
| READY | Можно выполнять в согласованном объёме |
| IN_PROGRESS | Сейчас выполняется |
| BLOCKED | Нужен конкретный доступ, ответ или внешнее изменение; причина записана |
| DONE | Критерий готовности проверен, доказательство есть в журнале |
| DEFERRED | Сознательно перенесена за текущий релиз |

Каждая задача имеет стабильный ID, зависимости, результат и ссылку на проверку. Обычно одновременно одна задача реализации `IN_PROGRESS`; подготовительные независимые проверки могут идти вместе. Блокировка одной задачи не мешает закончить остальные разрешённые работы.

## Цикл изменения

1. Прочитать статус/план/последний журнал. Проверить рабочее дерево и исходную ветку; не уничтожать чужие изменения.
2. Выбрать готовую задачу и отметить начало. Для неоднозначного нового требования записать решение, а не незаметно менять архитектуру.
3. Сделать минимальную завершённую часть, соблюдая границы domain, simulation, capture/editor, renderer, transport и storage.
4. Запустить необходимые проверки. Для документации: ссылки, согласованность и отсутствие секретов. Для runtime: unit/integration по поведению. Для схем: совместимость/валидация. Для UI: проверка в браузере; для устройства — реальный тест устройства.
5. Прочитать diff, проверить отсутствие временных файлов/секретов, затем отметить результат в журнале и задачах.
6. Выполнить `node tools/check-repository.mjs --staged` перед коммитом и `node tools/check-repository.mjs --history` перед push. На CI выполняется тот же контролируемый набор.
7. Commit message — только фактическая UTC-дата. После commit проверить author, committer, email и сообщение. Публиковать только в согласованный репозиторий.

## Git

Identity: `ydadev <300869099+ydadev@users.noreply.github.com>`, локальный `user.useConfigOnly=true`, hooks из `.githooks`. Настройка глобальной личной identity не используется для проекта. GPG-подпись с личным сертификатом по умолчанию отключена локально; безопасную подпись можно добавить отдельным решением.

Начальное наполнение пустого репозитория выполняется в `main`. Следующая разработка — небольшими ветками `task/<ID>-<short-slug>` и проверяемыми изменениями. Ветки и PR не содержат персональных сведений. Если используется merge/squash, итоговое сообщение и metadata тоже проходят правило даты/`ydadev`; автоматические стандартные merge messages не подходят.

## Проверки и выпуск

Документировать команду/сценарий, среду, ожидаемый и полученный результат. Статусы проверок: PASS, FAIL, NOT_RUN. Не писать «все тесты пройдены», если запускалась только одна категория. Не добавлять бессодержательные тесты, повторяющие реализацию.

Версии сборочных инструментов и зависимостей закрепляются при создании каркаса; `latest` не используется для воспроизводимого релиза. Runtime-контейнеры фиксируются по digest. Конфигурация секретов отделена от репозитория. Миграции версионируются; опасные изменения требуют backup и проверенного пути восстановления.

Перед обновлением работающего окружения: записать версии/образы, проверить backup и свободный диск, развернуть, выполнить health/reconnect smoke-test. При ошибке откатить образы и совместимую конфигурацию, не выполнять произвольный откат схемы БД. Для необратимой миграции применяется отдельный план восстановления.

Инфраструктурная готовность не заменяет готовность приложения. `/health/infra` проверяет только gateway; backend readiness и end-to-end сценарии должны иметь собственные проверки.
