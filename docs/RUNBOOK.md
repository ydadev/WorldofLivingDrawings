# Эксплуатация подготовленного окружения

Все команды ниже предназначены для администратора сервера. SSH-адрес и путь к ключу берутся из локального приватного инвентаря; секреты не копируются в терминальный вывод или Git. `docker` выполняется через sudo: членство пользователя в группе docker не требуется.

## Проверка

```sh
curl --fail https://world.routx.ru/health/infra
sudo systemctl is-active nginx docker
sudo nginx -t
sudo docker compose --env-file /etc/ldw/runtime.env -f /opt/ldw/infra/compose.yaml ps
sudo ufw status
sudo systemctl list-timers ldw-backup.timer
```

Ответ `application: not_deployed` ожидаем на этапе подготовки. Нет теста производительности или готового приложения. Временный `/__infra/ws` после проверки должен возвращать 404.

## Резервная копия

```sh
sudo systemctl start ldw-backup.service
sudo systemctl status ldw-backup.service --no-pager
```

Результат: `/opt/ldw/.local/backups/<UTC timestamp>/database.dump`, `blobs.tar.gz`, `config.tar.gz`, `manifest.json`, `SHA256SUMS`. Скрипт проверяет хеши и размеры до переименования частичной копии в завершённую. Каталог закрыт от обычных пользователей. Конфигурационный архив содержит секреты и должен оставаться защищённым; его нельзя прикладывать к issue/PR. В локальном проекте копии также лежат в `.local/backups/`, игнорируются Git и дополнительно запрещены policy checker. Не применять `git add -f` к `.local`.

Таймер запускает локальную копию раз в сутки, хранение на этапе подготовки — 14 дней. Неудачный запуск остаётся failed в systemd; внешнего оповещения пока нет. Первичная проверенная копия переносится в локальный проект вручную по SSH. Это не настроенная ежедневная внешняя репликация.

Скрипт согласованной копии и manifest прошёл CI и установлен на runtime-сервере. Проверены целостность и восстановление дампа в отдельную БД. До загрузки пользовательских рисунков нужно проверить восстановление сцены с приватной текстурой и продолжение симуляции после развёртывания приложения.

## Проверка восстановления БД без изменения рабочей БД

1. Выбрать копию и проверить `sha256sum -c SHA256SUMS` в её каталоге. Для копии нового формата вызвать `verify_backup_manifest` из `infra/backup-manifest.sh`; проверить также содержимое tar-архивов.
2. Убедиться, что временной БД `ldw_restore_check` нет; не удалять неизвестную существующую БД.
3. Создать `ldw_restore_check` через `docker exec ldw-db-1 createdb -U postgres ldw_restore_check`.
4. Передать `database.dump` на stdin `docker exec -i ldw-db-1 pg_restore -U postgres -d ldw_restore_check --exit-on-error`.
5. Проверить ожидаемые таблицы/строки. Удалить только созданную для этой проверки `ldw_restore_check` через `dropdb`.

На этапе подготовки проверено восстановление контрольной строки. Полный disaster recovery потребует чистого окружения, установки тех же версий/ролей, восстановления blobs/config и проверки прав пользователя. Восстановление рабочей БД поверх существующих данных не выполняется автоматически. Роли и секреты должны соответствовать конфигурации; при изменении пароля недостаточно поменять файл — существующая БД требует ALTER ROLE.

## Обновления и откат

Перед изменением сохранить копию, digest образа и конфигурацию. Обновлять minor-версии после проверки; не заменять volume и не выполнять `docker compose down -v`. Возврат к прежнему образу допустим только при совместимом формате данных/схем. Для major PostgreSQL нужен отдельный план миграции.

Системные security updates выполняет unattended-upgrades; это не обновляет прикладные контейнеры. Проверять `/var/run/reboot-required`. После контролируемой перезагрузки проверить домен, PostgreSQL health и отсутствие failed units.

Если NPM меняет внутренний адрес, сначала добавить разрешение нового адреса на HTTP:80 и проверить доступ, затем убрать старое. Docker-порты не публиковать без проверки firewall: Docker может обходить обычные UFW-правила для опубликованных портов.

## Первичная установка на новом сервере

Прочитать `infra/bootstrap-ubuntu.sh`, выполнить как root на Ubuntu 24.04; скопировать `infra/` в `/opt/ldw/infra`. Затем создать секреты на сервере, закрепить проверенный digest в `/etc/ldw/runtime.env`, настроить nginx, firewall по фактическому NPM и таймер. Не запускать неизвестные команды из журналов. Описанная первичная настройка не является автоматическим disaster recovery.

Изменения записывать в [WORKLOG.md](WORKLOG.md), проверки и блокировки — в [TASKS.md](TASKS.md), краткое актуальное состояние — в [STATUS.md](STATUS.md).
