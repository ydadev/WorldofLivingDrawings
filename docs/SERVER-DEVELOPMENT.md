# Серверный каркас CORE-02/03

Код `crates/ldw-server` пока проверяется в Ubuntu CI с временной PostgreSQL. Он не развёрнут на рабочем сервере и не заменяет инфраструктурную страницу.

`cargo test -p ldw-server --locked` применяет миграцию к тестовой PostgreSQL из `DATABASE_URL`. Проверка использует отдельную временную БД: она создаёт Admin, двух Owner, сессии, сцены, приглашения и доступы, поэтому её нельзя направлять на рабочую БД. CI дополнительно запускает `cargo fmt --all -- --check`.

Для будущего запуска процесса нужны защищённые файлы вне Git: `LDW_DATABASE_URL_FILE` указывает на файл с URL отдельной роли приложения, `LDW_PIN_KEY_FILE` — на ровно 32 случайных байта HMAC-ключа. Оба файла доступны только процессу сервера. `LDW_PUBLIC_ORIGIN` — точный HTTPS-origin сайта, `LDW_BIND_ADDR` — адрес внутри доверенной сети/gateway. Секреты не передаются аргументами команд и не записываются в `.env` репозитория. Смена HMAC-ключа инвалидирует действующие PIN-приглашения.

После миграции локальный оператор запускает `ldw-server bootstrap-admin <login>` и вводит пароль в скрытом терминальном запросе. Повторный bootstrap отвергается. Публичного пароля по умолчанию нет. `ldw-server serve` поднимает HTTP API и `/health/ready`; он не управляет TLS. Для первого публичного развёртывания ещё нужны production Docker image, закрытый маршрут через nginx/NPM, проверка доверенного IP для rate limit и эксплуатационный smoke-test. Этот документ не является командой для развёртывания.

API использует host-only `Secure; HttpOnly; SameSite=Strict` cookie, точное совпадение `Origin` и отдельный CSRF-токен для мутаций. Owner создаёт сессию и пятиминутное приглашение, Controller входит по QR/PIN. В БД хранятся только хеши токенов, PIN и код активации TV защищены HMAC. Получение сцены проверяет сессию в SQL-запросе; доступ одной сессии не подходит к другой. Сервисный код не выводит секреты в обычные журналы.

Viewer на том же устройстве Owner выдаётся через `POST /api/sessions/{sessionId}/viewers` с телом `{"interact":false}` либо `true`, Owner-cookie, Origin и CSRF. Для другого устройства, в том числе встроенного браузера TV, путь без ввода Owner-пароля на экране: TV вызывает `POST /api/sessions/{sessionId}/viewer-claims` и показывает восьмизначный код; сервер сохраняет хеш кода и кладёт 5-минутный claim-secret в HttpOnly-cookie TV. Ответ TV содержит отдельный claim-CSRF для заголовка активации. Owner вводит показанный код в `POST /api/sessions/{sessionId}/viewer-claims/approve` с нужным `interact`, своим cookie/CSRF. TV повторяет `POST /api/sessions/{sessionId}/viewer-claims/{claimId}/activate` с claim-cookie и claim-CSRF: до одобрения ответ `202 VIEWER_PENDING`, после одобрения получает Viewer-cookie и CSRF. Код и claim-secret не попадают в URL; активация одноразовая. Разрешено максимум два действующих Viewer-grant на сессию. Готовый пользовательский экран для этих запросов ещё предстоит сделать.

WebSocket `GET /api/sessions/{sessionId}/ws` требует точного Origin и действующего Owner/Controller/Viewer-cookie. Сразу после upgrade клиент за 5 секунд отправляет `{"type":"hello","csrf":"..."}`; после проверки приходит `snapshot` с версией, `sceneEpoch`, `revision`, `simulationTick`, состоянием и временем сервера. Команда имеет `type=command`, `commandId`, `sessionId`, `sceneId`, `sceneEpoch`, `interactionId`, `point:{x,y}` и `expiresAt` в Unix миллисекундах. Сервер сохраняет ACK и событие в одной транзакции; известный ID возвращает прежний исход, изменённое тело — `COMMAND_CONFLICT`. `{"type":"status","commandId":"..."}` запрашивает исход при потере ACK. Последующие `delta` идут в порядке revision; при разрыве/смене epoch новое соединение получает свежий snapshot. При старте единственного процесса runtime повышает epoch активных сцен, поэтому неизвестные старые клики не исполняются после рестарта. Controller-соединение обновляет heartbeat через 5 секунд; после 60 секунд без heartbeat его слот свободен, а переподключение снова проверяет лимит 10. Read-only Viewer видит сцену, но его действия получают `READ_ONLY`. Хранилище событий позволяет дочитать результат после рестарта процесса при сохранной БД.

На этом этапе принятое действие сохраняется как `interaction_requested` для будущего симулятора. Поведение рыб, ресурсные квоты и полный tick относятся к CORE-04/MVP-03. Отзыв устройств, защита Owner-входа от перебора и полный пользовательский интерфейс относятся к следующим задачам; runtime пока не production-готов.
