# Эксплуатационные правила первого релиза

Дата: 28 сентября 2026 года. Часть [ТЗ 1.1](TZ-1.1.md).

Правила подготовлены по поручению пользователя. Здесь заданы стартовые значения для реализации; администратор может менять параметры в конфигурации с валидацией совместимости. Изменение лимита не удаляет существующие рисунки и не отменяет уже принятые операции. Это спецификация поведения, а не инструкция выполнить удаление или настройку текущего сервера.

## 1. Базовые принципы

- Сервер — единственный источник истины. Клиентский таймер, повторный клик и состояние вкладки не определяют результат события.
- Успешное подтверждение означает, что устойчивое изменение записано. Отсутствие ответа не означает, что команда не выполнена.
- Рисунки и сцены сохраняются автоматически до явного удаления; отсутствие пользователей не запускает автоматическое удаление.
- Лимиты ограничивают новые операции. При заполнении мира существующий рисунок не вытесняется новым.
- Пауза, завершение показа и удаление — разные действия.
- Все решения о правах, квотах, времени и порядке команд проверяются сервером повторно.

## 2. Сессия, сцена и время

`Session` объединяет устройства и права. `Scene` — сохраняемый мир с рисунками, версиями контента и логическим состоянием. В сессии одна активная сцена; несколько экранов видят её из одного фиксированного ракурса. Различаться могут размер изображения и качество. Controller может быть телефоном, планшетом или компьютером; все такие подключения входят в общий лимит Controller.

`revision` — последовательность устойчивых изменений сцены. `simulationTick` — логическое движение внутри текущего состояния. `sceneEpoch` — поколение активной сцены в сессии: меняется при сбросе, смене/повторном открытии сцены и восстановлении runtime после перезапуска. Устаревшая epoch запрещает исполнить старую команду даже при совпадающем sceneId.

Длительность кормления, проход лодки и прогресс поведения измеряются логическим временем. Срок токенов, срок хранения, идемпотентность, ограничения частоты и время жизни приглашения — серверным реальным временем UTC. Изменение часов телефона не влияет на них. На сервере обеспечивается синхронизация времени; длительности внутри процесса измеряются монотонными часами.

Состояния показа:

| Состояние | Поведение |
|---|---|
| Running | Движение, добавление рисунков и взаимодействия доступны по правам |
| Paused | Положения и логические таймеры заморожены, новый корм/лодка не запускаются; добавление рисунка допустимо, новая рыба появляется неподвижно |
| Closed | Новые команды и загрузки запрещены, приглашения и Controller-доступ отозваны; рисунки сохранены, экран показывает завершение показа |

Owner может поставить/снять ручную паузу. При ручной паузе и возобновлении epoch также обновляется, чтобы отложенная команда не сработала после возобновления. Ручная пауза не снимается подключением нового устройства.

Если нет наблюдающего Viewer или Controller с открытым видом мира, сервер через 60 секунд приостанавливает сцену автоматически. Открытие вида возобновляет только такую автоматическую паузу. Controller, занятый только съёмкой или рисованием в редакторе, не поддерживает движение бесконечно; может добавить рисунок в автоматически приостановленную сцену.

Отключение последнего экрана не удаляет сцену и не отзывает сразу доступ остальных устройств. Автоматически приостановленная сцена освобождает слот активной симуляции; при возобновлении проверяется лимит активных сессий. Если слот занят, показ остаётся на паузе с понятной причиной.

«Завершить показ» сохраняет рисунки, отменяет временные события с очисткой ресурсов, закрывает сессию и оставляет возможность Owner открыть сцену снова с новыми приглашениями. «Очистить мир» — отдельная операция с описанием числа удаляемых объектов и подтверждением владельца.

## 3. Роли и права

Owner/Admin имеют собственный вход. Ребёнку аккаунт не требуется. Controller получает непривязанный к имени ребёнка `participantId` и доступ только к конкретной сессии. Авторство объекта хранится по participantId.

| Операция | Viewer | Viewer + interact | Controller | Owner | Admin |
|---|---|---|---|---|---|
| Просмотр активной сцены | Да | Да | Да | Да | Да |
| Корм и лодка | Нет | Да | Да | Да | Да |
| Добавление бумажной/цифровой раскраски | Нет | Нет | Да | Да | Да |
| Удаление/возврат своего рисунка | Нет | Нет | Да | Да | Да |
| Удаление/возврат чужого рисунка | Нет | Нет | Нет | В своих сессиях | Да |
| Отмена активной лодки/корма | Нет | Нет | Нет | В своих сессиях | Да |
| Пауза, закрытие, очистка, открытие сцены | Нет | Нет | Нет | В своих сессиях | Да |
| Выдача/отзыв устройств, приглашения | Нет | Нет | Нет | В своих сессиях | Да |
| Пакеты, общие лимиты, backup/restore | Нет | Нет | Нет | Нет | Да |

Создание сессии доступно Owner/Admin; анонимный пользователь не создаёт неограниченно новые миры. При первичном развёртывании создаётся Admin без общедоступного пароля по умолчанию; доступ владельца выдаётся им. Открытие ссылки Viewer само по себе не выдаёт административные полномочия.

Controller удаляет только свои пользовательские Entity. Служебную лодку и элементы мира удалить этим правом нельзя. Потерявший доступ Controller не доказывает авторство по ID картинки: Owner может восстановить объект или выдать новый доступ. Отзыв устройства не удаляет созданные им рисунки.

Каждая мутация, WebSocket-подключение и запрос приватной текстуры проверяют текущие права. Доступ одной сессии не подходит к другой. При cookie-auth используются Secure/HttpOnly/SameSite, проверка Origin и CSRF-защита мутаций. Долгоживущие секреты не хранятся в URL или localStorage.

## 4. Приглашения и устройства

Owner открывает окно подключения на 5 минут. На Viewer показываются QR и шестизначный PIN, привязанные к сессии. QR использует криптографически случайный секрет не менее 128 бит; PIN — короткий способ подключения с отдельным ограничением попыток. Приглашение выдаёт только Controller-права.

В течение окна приглашение допускает несколько телефонов до лимита. Это явно многоразовое приглашение, а не обещание одноразового PIN. Новый PIN/закрытие окна сразу инвалидируют прежний PIN/QR. Уже выданный доступ продолжает работать до отзыва/истечения. Owner может включить предварительное одобрение подключений при публичном показе; по умолчанию действует доступ по приглашению.

Стартовые сроки и ограничения:

| Параметр | Значение |
|---|---|
| Окно PIN/QR | 5 минут |
| Неудачные попытки pairing | До 5 в минуту на клиентский идентификатор, 30 в минуту на IP и 60 в минуту на сессию; превышение даёт временный retryAfter |
| Controller-доступ | До 12 часов с момента выдачи и не более 2 часов без пользовательской активности |
| Viewer-доступ | 7 суток с возможностью отзыва; хранится как доверенное устройство конкретной сессии |
| Освобождение места отключённого Controller | Через 60 секунд без heartbeat; старое удостоверение остаётся, но переподключение проверяет свободное место |

Heartbeat не считается пользовательской активностью для продления Controller-доступа. Рисование, как и нажатие кнопок, считается пользовательской активностью; онлайн-клиент передаёт ограниченную по частоте отметку активности без штрихов/изображения, не чаще одного раза в 15 секунд. Абсолютный срок доступа 12 часов не продлевается этим способом. После истечения устройство переподключается через действующее приглашение; Owner может сохранить participantId при подтверждённом продолжении старого доступа, но не на основании произвольного параметра клиента. Готовый preview/текущий рисунок остаётся в памяти открытой страницы до повторного входа.

Телевизионный read-only доступ и Owner-вход разделены. Выход владельца из админ-интерфейса не останавливает уже авторизованный экран. Закрытие сессии запрещает дальнейшее чтение рисунков Controller; Viewer может показать служебный экран «Показ завершён» без доступа к прежним текстурам.

## 5. Команды, повторные нажатия и одновременные действия

Минимальный конверт мутации:

```text
commandId (случайный уникальный ID)
sessionId, sceneId, sceneEpoch
type, payload
expiresAt (срок исполнения новой команды)
```

Идентификатор автора выводится из доступа. Сервер хранит результат по `(sessionId, participant/deviceId, commandId)` и хешу исходного тела 24 часа. Повтор того же запроса возвращает тот же результат без повторного эффекта. Повтор ID с другим телом возвращает `COMMAND_CONFLICT`. Неудача операции тоже получает определённый результат; после исправления причины новое осознанное действие получает новый ID.

Порядок обработки: проверка доступа → поиск известного commandId → проверка epoch/срока/прав/квот → сериализованное изменение состояния → транзакционная фиксация → подтверждение → публикация. Известный результат можно вернуть после смены epoch, но он маркируется исходной сценой и не применяется к текущей. Новая команда старой epoch отклоняется.

Для корма и лодки `expiresAt` не дальше 10 секунд вперёд от серверного времени; для остальных обычных мутаций, включая удаление/восстановление/паузу, — не дальше 60 секунд. Клиент получает оценку времени при подключении. Просроченный новый запрос не исполняется. Повторный запрос сохраняет исходное expiresAt; он не превращается в новую команду. После перезапуска неизвестные старые запросы дополнительно отсекаются сменой epoch. Поэтому очистка 24-часовой таблицы результатов не позволяет старому клику, в том числе удалению после последующего восстановления объекта, ожить позже.

Финализация upload проверяет как срок новой команды, так и срок intent. Получение уже сохранённого результата intent является чтением, доступно после этих сроков при действующих правах и не выполняет мутацию повторно.

До ответа кнопка отправленного действия временно занята. Сетевой повтор использует прежний ID. Быстрый второй пользовательский клик, если он всё-таки создал новый ID, проходит cooldown и общие квоты. Во всех клиентах ограничения отображаются из серверного состояния, а не вычисляются независимо.

Одна сцена имеет одну очередь логических команд. Два запуска последней доступной лодки/последнего свободного места не проходят одновременно: один принимается, второй получает актуальную причину отказа. Корм и лодка могут существовать вместе, но угроза имеет приоритет над едой. Квоты учитывают все устройства, а не отдельно каждую вкладку.

Общий предел мутаций — 5 запросов/секунду на участника с burst до 10; специальные cooldown кормления/лодки строже. Неудачная попытка не расходует квоту события, но учитывается в ограничении запросов.

## 6. Добавление рисунка без дублей и потери preview

Путь добавления: локальная съёмка либо цифровое рисование → общий preview → «Оживить» → получение uploadIntent → загрузка нормализованной текстуры → серверная проверка → транзакционное создание Entity со ссылкой на blob → подтверждение. `uploadIntent` действует 10 минут и фиксирует sessionId, sceneId, epoch, тип модели и версию шаблона. Долгое рисование не создаёт intent и не занимает место в мире до нажатия «Оживить».

На intent кратковременно резервируются слот Entity и допустимые байты; число активных intents ограничено 1 на Controller и 10 на сессию. Неиспользованная резервация освобождается через 2 минуты без продвижения; живой intent при продолжении повторно проверяет квоты. Готовая загрузка сама по себе не означает добавления Entity.

Завершение одного intent атомарно возможно только один раз и сохраняет `resultEntityId` в течение жизни сцены. Даже после истечения 24-часового кеша commandId повтор финализации известного intent не создаёт новую рыбу. Запись завершённого intent сохраняется при удалении Entity до удаления самой сцены, чтобы старый запрос не восстанавливал её.

Две одинаковые текстуры из фото или редактора не считаются случайным дублем автоматически: пользователь вправе осознанно добавить второй такой рисунок с новым intent. Blob может быть переиспользован, но экземпляры и авторство различаются. На время отправки фиксируется неизменяемая версия рисунка; последующие штрихи не меняют уже отправляемое содержимое. После успеха показывается результат, а повторное добавление доступно отдельным действием «Добавить ещё» с новым intent; сетевой повтор не создаёт его.

При заполнении мира приложение показывает «В мире уже 100 рисунков. Владелец может освободить место». Preview/цифровой рисунок остаётся в памяти открытой страницы; пользователь может скачать нормализованную раскраску или явно сохранить цифровой черновик на своём устройстве. Постоянный локальный кеш полученных с сервера рисунков не создаётся. Локальные черновики редактора регулируются отдельным правилом ниже. Без сохранения закрытие/выгрузка страницы может потребовать повторного фото/рисования.

При смене сцены загрузка старой epoch не направляется в новую автоматически. После возвращения пользователь видит сохранённый preview и явно повторяет добавление в актуальную сцену. Если прежнее добавление уже подтверждено, интерфейс показывает его исходную сцену, а не создаёт копию.

### 6.1. Цифровые черновики

Работа в открытом редакторе ведётся в памяти. Кнопка «Сохранить черновик на этом устройстве» включает для выбранного рисунка локальное сохранение и дальнейшее автосохранение изменений. В интерфейсе показано «Черновик хранится на этом устройстве»; на общем устройстве пользователь может оставить режим работы без постоянного сохранения. Это не серверное хранение и не синхронизация между устройствами.

После включения сохраняются текущий пользовательский слой, ID/версия шаблона и модели, необходимые безопасные данные силуэта/маски, версия формата редактора и время изменения. Камерный оригинал, токены доступа, идентификаторы аппаратного стилуса и телеметрия штрихов в черновик не добавляются. Undo-история может не сохраняться; продолжение восстанавливает текущий рисунок как базовое состояние.

Запись в IndexedDB выполняется транзакционно после завершённого действия с задержкой до 2 секунд. Длинный штрих может получать промежуточный checkpoint не чаще одного раза в 5 секунд; только успешная запись меняет статус на «Сохранено». До подтверждения сохранения интерфейс показывает «Сохраняем…». Выход в фон не считается гарантией, что последняя асинхронная запись успеет выполниться.

Один черновик редактирует одна вкладка. При обнаруженном конфликте второй вкладке предлагается открыть копию; более новая ревизия не перезаписывается старой молча. Смена шаблона создаёт отдельный черновик. Обновление пакета не перенатягивает старый рисунок автоматически; недоступная версия допускает локальный просмотр/PNG, а «Оживить» требует установленную совместимую версию.

На один браузерный профиль: до 10 черновиков, суммарно до 64 МиБ, без автоматического удаления по возрасту. При исчерпании лимита или квоты браузера старые работы не удаляются, новый рисунок остаётся в памяти и предлагается скачать PNG/удалить выбранный старый черновик. Если IndexedDB недоступна, редактор остаётся работоспособным, но не сообщает об успешном постоянном сохранении. Браузер может очистить своё хранилище, поэтому локальный черновик не является гарантированной резервной копией. [MDN: хранение и квоты](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

Публикация рисунка, закрытие удалённой сессии и истечение Controller-доступа не удаляют явно сохранённый локальный черновик. При выходе пользователь может выбрать очистку черновиков этого устройства; в списке черновиков доступно удаление. Локальная работа не даёт прав на удалённую сессию: для публикации после истечения доступа требуется новое подключение и проверка текущего мира.

Цифровые черновики не занимают 100 слотов сцены, не расходуют серверную квоту blobs и не входят в серверный backup. После «Оживить» сервер хранит готовую Paint Texture на общих условиях, а последующее изменение черновика не меняет опубликованную рыбу автоматически.

## 7. Сеть, перезапуск и перегрузка

При известном разрыве сокета управление блокируется сразу. При потере связи без явного закрытия она определяется heartbeat; интервал 5 секунд, потеря двух последовательных ответов означает разрыв. Браузер может кратко продолжить только визуальное движение, затем замирает с индикатором связи; сервер при этом может продолжать мир для остальных клиентов.

Переподключение: задержки 1, 2, 4, 8 секунд, затем до 15 секунд между попытками с небольшим случайным разбросом. Возвращение сети/вкладки запускает проверку доступности сразу. Требуется действующая авторизация.

При восстановлении сначала загружается свежий snapshot/delta, затем снимается блокировка действий. Для команды с неизвестным результатом запрашивается статус исходного commandId/intent. Неизвестное истёкшее действие не повторяется как новый клик. Клиент показывает «Действие не подтверждено, попробуйте снова». Очередь кормлений/лодок за время офлайна не накапливается.

Локальная обработка фото и цифровое рисование могут продолжаться без связи после загрузки нужных ресурсов; загрузка/добавление ждут её возвращения и повторной проверки сцены. При потере доступа редактор не очищает незавершённую работу. Новая Entity не появляется авторитетно только потому, что клиент показал preview.

Checkpoint каждые 5 секунд сочетается с транзакционным журналом устойчивых изменений. При рестарте логическое время простоя не проигрывается мгновенно; сохраняются остатки корма/назначения и подтверждённые изменения. При replay semantic events не списываются повторно уже учтённые ресурсы и не повторяются стартовые звуки. Невозможность загрузить согласованное состояние приводит к явной ошибке сцены, а не к её молчаливому обнулению.

При перегрузке новые тяжёлые операции ограничиваются/отклоняются до принятия, существующие сцены сохраняют приоритет. Коды ошибки сопровождаются retryAfter, если это временное ограничение. Критический отказ записи БД/диска запрещает подтверждать мутации; клиент видит недоступность сохранения.

## 8. Стартовые квоты

Все квоты серверные и атомарно учитывают активные резервации. Пониженный администратором лимит блокирует новые операции до соответствия, но не удаляет существующее содержимое.

| Ресурс | Стартовый лимит |
|---|---|
| Одновременно симулируемые сессии на установку | 3 |
| Одновременно подключённые Controller на сессию | 10 |
| Viewer на сессию | 2; дополнительные виды на телефонах входят в Controller |
| Локальные черновики редактора | До 10 на браузерный профиль, суммарно 64 МиБ; только при явно включённом сохранении |
| Холст цифрового редактора / история | 1024×1024; до 50 Undo-действий с бюджетом 32 МиБ; результат для сервера 512×512 |
| Пользовательские Entity в активной сцене | 100 |
| Служебная лодка | 1 дополнительный слот |
| Источники корма | 3 на сцену |
| Сохранённые сцены | 20 на Owner, 100 на установку; архивные входят в этот лимит |
| Нормализованная Paint Texture | 512×512; только однокадровые PNG/WebP, не более 2 МиБ загрузки; анимированные файлы отклоняются |
| Декодированная Paint Texture | Ровно 512×512; не более 262 144 пикселей; проверяются реальные размеры |
| Пользовательские blobs одной сцены | 256 МиБ вместе с корзиной и резервированием |
| Пользовательские blobs установки | 20 ГиБ физического хранилища; все ссылки авторизуются независимо от deduplication |
| Штатные пакеты | 10 ГиБ установки; один пакет до 256 МиБ архива и 512 МиБ распаковки |
| Содержимое пакета | До 2 000 файлов; коэффициент распаковки до 100; decoded budgets проверяются отдельно |
| Одновременное серверное декодирование рисунков | 1 CPU-задача, очередь до 20; длительность задачи до 10 секунд |
| Установка пакета | 1 задача; недоступна Controller; отдельные лимиты и низкий приоритет |

Для byte-квоты сцены размер каждого различного blob учитывается один раз внутри сцены, даже если на него ссылаются несколько Entity; scene-лимит проверяется также при повторном использовании blob другой сцены. Это не позволяет обходить квоты дедупликацией между владельцами. Системные пакеты не списываются из квоты детских рисунков.

Raw photo не относится к серверному upload: оно обрабатывается локально с ограничением памяти и ранним уменьшением. Загрузка исходного снимка вместо Paint Canvas отклоняется.

Картинка без корректного шаблона, с неверными размерами или декодированием отклоняется до создания Entity. Сервер перепроверяет тип, декодирует в ограниченной среде, удаляет метаданные, повторно кодирует и назначает безопасный ID. Одна проверка MIME/расширения недостаточна.

Если свободно меньше `max(5 ГиБ, 10% тома данных)`, приостанавливаются новые upload/package install и создание новых сцен, выдаётся предупреждение Admin. Мутации небольшого объёма допускаются только при успешной записи. Достижение порога не запускает удаление старых рисунков. Перед очисткой/сжатием журнала учитываются требования восстановления.

Корм: 10 порций, 15 секунд, максимум 10 участников источника; cooldown 1 секунда на участника и 0,5 секунды на сцену. Лодка: максимум 30 секунд, cooldown 10 секунд на сцену плюс запрет второго экземпляра до окончания первого. Пауза останавливает длительность события; cooldown и защитные ограничения продолжают идти по серверному времени.

## 9. Хранение, удаление и очистка

| Данные | Политика |
|---|---|
| Рабочие сцены и добавленные рисунки | Автосохранение до явного удаления, без удаления по неактивности |
| Явно сохранённые цифровые черновики | На устройстве до удаления пользователем/очистки браузера; серверного срока хранения и backup нет |
| Удалённые Entity/сцены | Корзина 7 суток; место текстур продолжает учитываться |
| Незавершённые upload/quarantine | До 24 часов; резервация слота освобождается раньше по правилу intent |
| Результаты commandId | 24 часа |
| Завершённые uploadIntent и resultEntityId | Пока существует сцена, включая её корзину |
| Semantic event journal | Хранить минимум 7 суток и все записи, нужные после последнего надёжного checkpoint; удаление только при доказанной покрытости сохранённым состоянием |
| Технические журналы | 14 суток, с ротацией и суммарным лимитом 1 ГиБ |
| Данные для авторизации | До истечения/отзыва, затем минимальные необходимые записи аудита без самих секретов |

Удаление собственной рыбы выполняется одним действием с кнопкой «Отменить» на 30 секунд. Доступ к восстановлению из корзины сохраняется 7 дней при действующих правах; Controller восстанавливает своё, Owner — любое в своей сессии. Если свободного слота уже нет, восстановление получает отказ, а рисунок остаётся в корзине до срока. Отмена не обходит лимит 100 объектов.

Массовая очистка, удаление сцены и окончательная очистка корзины требуют подтверждения в интерфейсе с количеством затронутых рисунков. Это правило продукта, а не необходимость подтверждать каждую техническую настройку при разработке.

Удаление рыбы сначала убирает её из активной сцены и отменяет задания/резервы. Текстура сохраняется на срок корзины. Истечение корзины убирает последние логические ссылки; фоновый GC удаляет невостребованный blob после защитного окна 24 часа. В активном мире, другой сцене, корзине или выполняемом backup нужный blob не удаляется.

Сброс мира создаёт новую эпоху, завершает временные действия и переносит пользовательские Entity в корзину одной операцией. Настройки мира и установленные шаблоны сохраняются. Первый релиз содержит один World; будущая смена World по умолчанию сохраняет прежнюю Scene, а не конвертирует рыбу в объект другого мира.

Уменьшение квоты и очистка технического кеша не являются основанием удалить детские рисунки. При заполнении Owner получает список способов освободить место: удалить ненужные рисунки/сцены, очистить свою корзину либо увеличить квоту через Admin.

## 10. Приватность и кеш

Не запрашиваются имя, дата рождения, контакты ребёнка и геолокация. Сеансы Controller не используют рекламные трекеры. В технические журналы не попадают токены, PIN/QR-секреты, сырые фотографии и содержимое рисунков.

Raw photo остаётся в памяти приложения, освобождается после получения preview/завершения процесса. Системная галерея и сделанные пользователем отдельные сохранения управляются пользователем/ОС. При закрытии сессии и выходе очищаются приватные данные, полученные из удалённой сцены, насколько доступно приложению. Собственный незавершённый цифровой рисунок не уничтожается из-за закрытия удалённой сессии; постоянное сохранение/очистка его локального черновика происходят по правилам §6.1.

Общие ассеты мира, модели и публичные шаблоны можно кешировать по content hash. Paint Textures выдаются через авторизованный endpoint с `Cache-Control: private, no-store`, не попадают в общий Service Worker cache и не получают общедоступную ссылку только по hash. Для текущего рендера допускается оперативный AssetManager с явным освобождением.

Удаление/отзыв доступа запрещают новые выдачи рисунка сразу. Приложение очищает известные ему клиентские ссылки и ресурсы; нельзя обещать удаление ранее сделанного пользователем снимка экрана или выгрузки файла.

## 11. Резервные копии и восстановление

На этапе подготовки по отдельному решению пользователя копии хранятся в `.local/backups/` папки проекта, исключённой из GitHub. Сервер делает локальные копии по таймеру, проверенная начальная копия перенесена в локальный проект. Автоматическое внешнее хранение отложено до рабочего запуска (INFRA-05); это временный порядок подготовки, а не выполненная политика восстановления при потере сервера, описанная ниже.

Ежедневный согласованный backup хранится вне рабочего сервера. Состав: PostgreSQL, необходимые blobs/packages, manifest версий/хешей и конфигурация восстановления. Секреты резервируются отдельно с ограниченным доступом; приватный ключ подписи пакетов не требуется держать на runtime-сервере.

Во время фиксации manifest и копирования GC не удаляет нужные blobs. Резервная копия считается успешной после проверки manifest/целостности и доставки во внешнее хранилище. Копирование одной БД без рисунков не считается полноценным backup.

Схема хранения: последние 7 ежедневных и 4 еженедельных копии, максимальный возраст 35 суток. Удалённый рисунок может оставаться в backup до этого срока; возврат старой копии не является обещанием восстановления последних изменений. Для удаления данных из backup действует естественное истечение копий, а не переписывание каждого архива.

Цели: RPO до 24 часов при потере сервера, RTO до 4 часов при доступном чистом сервере и хранилище backup. Проверка восстановления выполняется до пилота, ежемесячно и после изменения формата backup/миграций. Это эксплуатационные цели, требующие измерения.

Восстановление в чистом окружении включает открытие сцены, получение приватной текстуры с правильными правами и продолжение мира. После аварийного restore все пользовательские сеансы/доступы устройств отзываются, Controller подключаются заново; это не удаляет рисунки. Admin-восстановление доступа документируется отдельно от публичного интерфейса.

## 12. Ответы интерфейса и проверка правил

| Ситуация | Сообщение / действие |
|---|---|
| Заполнено 100 мест | «В мире уже 100 рисунков. Попросите владельца освободить место»; preview сохраняется в открытой странице |
| Точка вне воды/рабочей области | «Выберите место внутри воды» |
| Лодка уже активна | «Подводная лодка уже плывёт. Дождитесь её ухода» |
| Cooldown | Показ оставшегося времени по данным сервера |
| Потеря связи | «Соединение потеряно. Подключаемся…»; действия недоступны |
| Смена сцены во время фото/рисования | «Мир изменился. Проверьте, куда добавить рисунок»; текущая работа не очищается |
| Ошибка сохранения цифрового черновика | «Не удалось сохранить на устройстве. Скачайте рисунок или освободите место»; работа остаётся в памяти |
| Истёк доступ | «Подключитесь к экрану заново»; без удаления готового preview из открытой страницы |
| Сессия закрыта | «Показ завершён. Рисунки сохранены у владельца» |
| Недоступно сохранение | «Сейчас не удалось сохранить. Попробуйте позже»; подтверждение успеха не показывается |

Минимальные проверки реализации: два клиента занимают последний слот; повтор commandId с тем же и другим телом; потеря ACK после успешного commit; повтор финализации upload после истечения кеша команд; reconnect с просроченным кликом; перезапуск посреди кормления; смена epoch во время upload; окончание доступа; удаление активного участника; восстановление из корзины при заполненном мире; GC с общими ссылками; восстановление согласованного backup. Эти проверки подтверждают поведение, а не только форму схемы.

Для редактора дополнительно проверить: длинное рисование без резервирования слота; перезагрузку явно сохранённого черновика; отказ IndexedDB/заполненную квоту; две вкладки одного черновика; недоступную старую версию шаблона; рисунок, изменённый во время отправки; потерю ACK после «Оживить»; отсутствие отправки штрихов/текстуры до команды публикации.
