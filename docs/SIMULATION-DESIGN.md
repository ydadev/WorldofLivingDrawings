# Simulation Core: первый инкремент CORE-04

`crates/ldw-sim` — чистое ядро логического движения в мировых единицах. Оно не знает о PostgreSQL, сети, Babylon и детских текстурах. Сервер остаётся единственным владельцем состояния; браузер впоследствии использует тот же код для интерполяции/предсказания с коррекциями от сервера. Вход `World::step` — одно логическое продвижение при 20 Hz, а не время рендера. При одинаковой начальной сцене и последовательности вызовов состояние воспроизводится.

Начальный API принимает прямоугольную область воды, до 16 круглых препятствий и до 100 рыб. Рыба имеет ID, позицию, скорость и цель; текущий режим — обычное плавание. Цель выбирается детерминированно из seed/ID/поколения. Короткий маршрут проверяет пересечение с препятствием и при необходимости выбирает обходную точку; каждый шаг дополнительно проверяет границы и весь отрезок движения. Случайная новая цель не используется как способ телепортации через препятствие. Конфигурацию геометрии передаст версия пакета мира, а не свободный код браузера.

`World::checkpoint()` выдаёт версионированный снимок с границами, препятствиями, полным состоянием маршрутов рыб, seed и логическим tick. `World::restore()` проверяет версию, геометрию, скорости, лимиты и уникальность ID до запуска. ID рыб сериализуется строкой из 32 шестнадцатеричных символов: UUID не теряет точность в PostgreSQL JSONB/`serde_json::Value`. Локальный тест проверил JSON/JSONB-подобный round-trip, точное продолжение маршрута после восстановления и отказ на повреждённые данные.

Серверный `simulation`-адаптер читает границы из версии пакета `content/underwater/world.json`, загружает `state.simulation` и сверяет её tick с колонкой `simulation_tick`. Если у сцены уже есть объекты, но нет checkpoint, загрузка завершается ошибкой вместо обнуления состояния. Сохранение меняет только поле `state.simulation` и `simulation_tick`, сохраняя параллельно записанные команды; сравнение epoch и предыдущего tick не даёт старому worker перезаписать новую версию. Тест PostgreSQL в Ubuntu CI прошёл.

При запуске сервера supervisor поднимает runner для активных сцен с сохранённым `state.simulation`. Runner шагает с интервалом 50 мс, проверяет статус/epoch раз в 20 ticks, сохраняет контрольную точку раз в 100 ticks и на штатном завершении процесса. Пропущенные интервалы не ускоряют логическое время. Тест с PostgreSQL на сокращённом реальном интервале проверил достижение 100 ticks, checkpoint, завершение по сигналу и отсутствие новой `revision` на каждую позицию; Ubuntu CI прошёл. Новая пустая сцена не запускает runner; атомарная публикация первой рыбы создаёт исходный checkpoint вместе с Entity.

Сборка для `wasm32-unknown-unknown` прошла локально и в CI и проверяет совместимость исходного ядра с браузерным target; загрузка именно этого модуля браузером ещё отдельная проверка.

Контрольные сообщения `positions` отправляются из памяти каждые 10 логических шагов (2 Hz), без новой строки журнала и без увеличения `revision`. Сообщение содержит schemaVersion, sceneId, sceneEpoch, revision применённого состояния, simulationTick, ID рыб, координаты и направление. ID Entity имеет вид `fish-<32 hex>`, совместимый со схемой контента; в checkpoint остаётся сам 128-битный ID. WebSocket доставляет сообщение только подписчикам той же сцены после snapshot; кадр с ещё не полученной клиентом revision пропускается. Клиент проверяет эпоху, ревизию и монотонный tick, затем передаёт координаты renderer adapter. Babylon плавно доводит уже существующие Entity до новых позиций за 500 мс; неизвестный ID не создаёт объект. Контракт, transport-тест, два WebSocket-клиента, PostgreSQL, WASM и Chrome-интерполяция прошли локально и в Ubuntu CI.

Babylon renderer загружает один GLB на вид и создаёт отдельный экземпляр модели и paint-материала для каждой Entity. Текстура рисунка задаётся через разрешённый приложением URL по `paintBlobId`, поэтому раскраска одной рыбы не меняет соседнюю. Прототип в Chrome проверил две рыбы одного вида с красной и синей PNG-текстурами, один запрос модели, раздельные материалы, интерполяцию и удаление; Ubuntu/Chrome CI прошёл. Путь загрузки реальных приватных рисунков сервером ещё не подключён; опытная сцена использует тестовые data-URL.

Начальный LOW-профиль ограничивает framebuffer 1280×720 даже при 4K canvas; `renderScale` регулируется от 1 до 0,5 и не включает тени или post-processing. Клонированные материалы работают без тяжёлого освещения. Локальный Chrome-тест подтвердил 1280×720 и 960×540 при эмуляции 4K-области. У первых кадров 100 GLB-рыб на программном GPU были задержки прогрева шейдеров. После 3 секунд прогрева 5-секундный локальный тест без индивидуальных рисунков дал p95 17–24 мс при 640×360–960×540; с 100 различными 512×512 PNG-текстурами — ~77 мс при 960×540 и ~52 мс при 640×360. [Ubuntu/Chrome CI](https://github.com/ydadev/WorldofLivingDrawings/actions/runs/36553908000) с 100 различными текстурами прошёл функционально, но измерил p95 ~180 мс при 960×540 на программном GPU. Значительная разница между средами требует профилирования, а не вывода о достигнутой производительности. Это не приёмка реального TV: нужны измерения на устройстве и 10-минутный сценарий с действиями.

Следующий инкремент LOW разделяет статические материалы глаз между экземплярами; только материал окрашиваемой поверхности и текстура отдельные для каждой рыбы. Временная сфера загрузки удаляется после появления GLB, постоянный родитель — TransformNode. Для 100 рыб Chrome-проба показала 400 mesh и 107 материалов; красная и синяя рыбы проверены по пикселям итогового кадра. Локальный p95 остался ~77–82 мс при 960×540, [Ubuntu/Chrome CI](https://github.com/ydadev/WorldofLivingDrawings/actions/runs/36556126350) — ~170 мс на программном GPU. Уменьшение числа объектов пока не ускорило кадр заметно.

Первую рыбу можно создать через доверенную серверную операцию `publish_first_fish`: одна транзакция блокирует сцену, проверяет активный подводный мир и свободное состояние, записывает Entity, checkpoint tick 0 и `entity_published` с новой revision. WebSocket передаёт её как delta с `upsert`; после этого supervisor обнаруживает сцену. Повторная попытка и точка вне воды отвергаются без частичной публикации. Это пока внутренний переход состояния: проверка владения PaintResult и публичный сценарий «Оживить» относятся к MVP-01/02. [Ubuntu/PostgreSQL/WASM CI](https://github.com/ydadev/WorldofLivingDrawings/actions/runs/36554955457) прошёл.

По [ADR-015](DECISIONS.md) следующие рыбы сначала попадают во внутреннюю долговечную таблицу `fish_publications`; запись не объявляется видимой Entity. Операция проверяет активную сцену, вид, точку, согласованность исходного checkpoint и сумму опубликованных/ожидающих рыб против лимита 100 под блокировкой сцены. Runner раз в 20 логических шагов берёт все ожидающие записи и на копии живого World создаёт рыб. Одна транзакция записывает checkpoint текущего tick, расширенный список Entity, последовательные `entity_published`/revision и удаляет очередь. Память runner меняется только после commit. При restart оставшиеся записи применяются новой версией runner; если commit успел завершиться, они уже удалены и находятся в checkpoint. [Ubuntu/PostgreSQL CI](https://github.com/ydadev/WorldofLivingDrawings/actions/runs/36558695594) живого runner, пакетной публикации и восстановления — PASS. Пока API вызывается только из доверенного серверного кода; владение blob и завершение upload относятся к MVP-01/02.

CORE-04 ещё не завершён: реакция на корм/лодку и достижение LOW-цели впереди. Между checkpoint позиции живут в памяти сервера; при аварийном рестарте восстановление откатывается к последнему сохранённому логическому шагу.

Ядро кормления теперь хранит до трёх источников в checkpoint: точку, десять порций, срок 300 логических шагов и ID рыб, уже получивших порцию. На каждом шаге подходящие рыбы в радиусе 3,75 мировых единицы получают цель около источника; порция списывается только при входе в зону радиуса 0,3. Рыба получает не больше одной порции от одного источника. Источник истекает даже без рыб, назначения освобождаются. Восстановление принимает и прежние checkpoint без поля корма; проверяет ограничения и продолжает то же движение/списание. Семь тестов ядра и WASM-сборка прошли. На этом этапе механизм существовал только в ядре; серверное применение команд описано ниже.

По [ADR-016](DECISIONS.md) сервер перед ACK кормления проверяет разрешённую точку, три общих активных/ожидающих источника, 0,5 секунды между кормлениями сцены и 1 секунду между кормлениями одного grant. Пустая сцена получает исходный checkpoint. ACK сохраняет намерение; runner на границе логического шага берёт его из `pendingInteractions` и одной транзакцией фиксирует обновлённый World, `activeActions`, удаление очереди и `interaction_state` с новой revision. Порция и истечение тоже создают атомарные checkpoint/событие; при рестарте уже съеденная порция не восстанавливается. Клиенту нужен отдельный визуальный слой источников и применение `interaction_state`; пока эти реакции есть в серверном состоянии и контракте, но не в рендере. Реальная проверка на PostgreSQL/Ubuntu ожидается.
