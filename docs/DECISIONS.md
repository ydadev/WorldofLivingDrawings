### ADR-020 — объёмное плавание при фиксированной камере

Локальный просмотр с перемещением рыбы только по X/Y не передавал объём аквариума. Выбрана третья мировая координата глубины Z в пределах от −1,5 (ближе к зрителю) до +1,5 (дальше). Сервер детерминированно выбирает цели по всем трём координатам, ограничивает шаг и сохраняет Z в checkpoint; 2 Hz кадр передаёт Z и направление по глубине. Корм находится на среднем слое Z=0 и списывается после приближения по глубине. При лодке рыба может отступить и по Z. Браузер отображает поворот 3D-модели, отдельное движение хвоста и умеренную разницу видимого размера между ближним и дальним слоями; это визуальный приём ортографической камеры, не изменение пользовательского ракурса. Декор имеет несколько слоёв Z, чтобы глубина читалась. Рассмотрены только экранное изменение размера и локальная анимация без серверного Z; оба варианта оставляли экраны и исход кормления несогласованными. Старые checkpoint восстанавливаются с Z=0. Это изменение CORE-04 и MVP-02; совместимость с физическим TV и бюджет кадра требуют отдельной проверки.

### ADR-019 — допуск симулируемой сессии

Supervisor запускает не более трёх сцен, но раньше первая рыба или первое событие пустой четвёртой сцены могли сохранить checkpoint без запуска runner. Тихая остановка мира нарушает подтверждённое сервером действие. Рассмотрены общий лимит на создание сессий (он блокирует пустые/несимулируемые сессии) и проверка числа сцен без сериализации (два конкурентных запроса могут занять один свободный слот). Выбран допуск в момент создания первого checkpoint: транзакция после блокировки своей сцены берёт общую PostgreSQL advisory lock, считает активные сцены со статусом сессии `running` и `state.simulation`, при числе 3 отклоняет новый старт без checkpoint/Entity/события. Блокировка удерживается до commit, поэтому конкурентный старт видит уже занятый слот. Пауза освобождает слот; повтор ранее отклонённой команды возвращает записанный отказ, новая команда проверяет квоту снова. Первый upload получает HTTP 409 `SIMULATED_SESSION_LIMIT`, корм/лодка — ACK с этим кодом. Рисунок остаётся у пользователя; повтор финализации возможен после освобождения слота. Изменение CORE-04 проверяется отдельным конкурентным тестом в чистой БД; общая БД прежних unit-тестов не является изолированной проверкой глобальной квоты.

### ADR-018 — хранение Paint Texture

Текущий `normalized_png` в `upload_intents` — ограниченный по времени карантин, а не место постоянного хранения. Постоянные детские текстуры хранятся на уже подготовленном томе `/var/lib/ldw/blobs`. ID — полные 64 символа SHA-256 проверенного нормализованного PNG. Файл находится только в вычисленном сервером пути `sha256/<первые два символа>/<ID>.png`; пользовательский путь не принимается. Повторная запись того же содержимого не заменяет файл. Права на выдачу определяются текущей ссылкой Entity/сцены и grant, не знанием ID. Рассмотренные варианты: хранить всё в PostgreSQL BYTEA (простая транзакция, но рост и нагрузка на БД) либо отдельные изменяемые файлы по UUID (сложнее восстановление и дедупликация). Выбраны неизменяемые файлы с учётом ссылок в БД для исходной конфигурации 2 vCPU/8 ГБ и готового persistent volume.

Для публикации сервер записывает файл во временный путь на том же томе, проверяет хеш, синхронизирует файл и каталог, атомарно размещает конечный файл без перезаписи существующего, затем фиксирует ссылку, квоты, результат intent и публикацию одной транзакцией БД. При ошибке до commit файл может остаться без ссылки, но Entity на отсутствующий файл не подтверждается. GC удаляет только доказанно невостребованный файл после 24 часов и не работает во время согласованного backup. Сцена учитывает размер каждого отличного blob один раз вместе с корзиной и резервированием; лимит — 256 МиБ, физический лимит установки — 20 ГиБ. Совпадающие файлы разных сцен не обходят квоту ни одной сцены. Необработанные фотографии и метаданные в blob не попадают.

Обновлённый `infra/backup-local.sh` использует экспортируемый снимок PostgreSQL и общую с финализацией/GC блокировку до окончания архивации неизменяемых файлов. Manifest формата 1 содержит версии и хеши трёх артефактов; проверка идёт до публикации завершённой копии. Скрипт прошёл Ubuntu/PostgreSQL CI, установлен на runtime-сервере и создал копию, восстановленную в отдельную БД. Из тестовой копии живой сцены в CI восстановлены два PNG, права доступа и checkpoint; до пилота нужна такая же проверка после развёртывания приложения на рабочем сервере. По решению пользователя копии пока остаются в `.local/backups/` проекта, исключённой из Git; внешнее зашифрованное хранилище — отдельный незакрытый этап INFRA-05.
