# Правила работы над World of Living Drawings

## Порядок начала и завершения работы

1. Прочитать `docs/STATUS.md`, `docs/TASKS.md`, последние записи `docs/WORKLOG.md` и относящиеся к задаче решения `docs/DECISIONS.md`.
2. Рабочие требования: `docs/TZ-1.1.md` и `docs/operating-rules.md`. ТЗ 1.0 и proposal — история, не источник отменённых требований. Последние указания пользователя имеют приоритет.
3. Выбрать следующую задачу `READY` с выполненными зависимостями; до изменения кода поставить `IN_PROGRESS`. Не начинать произвольную новую функцию вне согласованного объёма. Если задача заблокирована, указать конкретную причину и продолжать независимую готовую работу.
4. Работать небольшими проверяемыми изменениями. Соблюдать `docs/DEVELOPMENT.md`; не смешивать несколько независимых этапов в одну непроверяемую поставку.
5. Выполнить проверки, относящиеся к изменению, и записать реальные результаты в `docs/WORKLOG.md`. Непроведённая проверка имеет статус `NOT_RUN`, а не `PASS`.
6. Обновить `docs/TASKS.md` и `docs/STATUS.md`: выполнено, осталось, блокировки, следующий шаг. `DONE` требует доказательства выполнения критерия готовности. Подготовленный скрипт не означает, что сервер уже настроен.
7. Перед commit/push выполнить проверку репозитория, метаданных Git и diff. Не оставлять секреты и персональные данные в истории.

## Обязательное правило Git и приватности пользователя

- Публичная идентичность пользователя — только `ydadev`. Не использовать его имя, фамилию, личную почту, имя локальной учётной записи, домашние пути или другие персональные данные в файлах, commit/PR, названиях веток, логах и Git author/committer.
- Author и committer: `ydadev`; email: `300869099+ydadev@users.noreply.github.com` — служебный GitHub noreply, не личная почта. Число — проверенный публичный ID аккаунта для корректной привязки GitHub.
- **Всё сообщение каждого коммита — только дата `YYYY-MM-DD` по UTC**, например `2026-09-28`. Никаких пояснений, заголовков, тел сообщений, подписей, `Co-authored-by` или других trailers. Дату брать фактическую в день коммита, не копировать дату примера.
- Подробности изменений, номера задач и проверки записывать в `docs/WORKLOG.md`, а не в commit message. Привязку к SHA можно добавить следующей записью журнала, без бесконечных amend ради собственного хеша.
- Настройка identity выполняется локально для репозитория, без изменения глобальной Git-конфигурации пользователя. Не отключать hooks/проверки ради обхода правила.
- Merge/squash/rebase тоже не должны создавать коммиты с другим сообщением или личной идентичностью. Перед публикацией проверять всю новую историю; не делать force push без отдельной необходимости и явного разрешения пользователя.
- Ключи, пароли, токены, приватные адреса/инвентарь сервера, дампы и сырые журналы хранятся только в игнорируемом `.local/` либо защищённых файлах сервера. В Git — конфигурационные шаблоны без секретов и обезличенные результаты.
- Не вставлять переданные пользователем секреты в команды с открытыми аргументами, файлы проекта или отчёты; пользоваться скрытым вводом/секретными файлами. Никогда не повторять пароль в ответах.

## Технические ограничения

- Первый релиз — один подводный мир, одна фиксированная камера, два пути раскраски (бумага и браузер), корм и лодка. Город, ферма и полные authoring tools не входят в текущую поставку.
- Авторитетная логика на сервере. Renderer не владеет бизнес-состоянием. Entity/World — версионированные данные без произвольного кода.
- Публичный HTTPS/WSS заканчивается на отдельном Nginx Proxy Manager. Сервер приложения принимает HTTP на 80. Не устанавливать там Certbot/ACME/Caddy для управления сертификатами и не менять NPM без необходимости.
- PostgreSQL и служебные порты не публиковать наружу. Forwarded-заголовкам доверять только от проверенного NPM. Не переносить секреты в Docker images.
- Не объявлять готовым весь проект или Smart TV по факту успешного smoke-test ПК. Разделять инфраструктурную проверку, тест приложения и нагрузочный тест.
- Не запускать подагентов без явного запроса пользователя или отдельного применимого указания.
